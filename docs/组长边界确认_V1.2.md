# 组长边界确认 V1.2

本文档记录本地工程已经采用的公共边界，后续模块负责人按这里接入。

## 选课结构化节次

`week_day`、`start_period`、`end_period` 属于公共契约，由组长统一放进：

- `course_section` 表
- `CourseSectionDTO`

模块负责人不要另建 `schedule_text` 作为核心判断字段。展示文字可以自己拼，但时间冲突必须使用结构化字段。

## 选课开放期

统一表名：`enroll_period`

字段：

- `term`
- `enroll_start_at`
- `enroll_end_at`
- `drop_end_at`

`CourseDAO` 统一提供 `findEnrollPeriod(Connection connection, String term)`。选课和退课时由选课模块在 service 层校验时间窗口。

## LMS 内容查询

`ClassroomContentQuery` 放在：

`edu.seu.vcampus.common.dto.classroom`

以下接口统一接收 `ClassroomContentQuery`，不能只用 `PageQuery`：

- `NOTICE_LIST`
- `RESOURCE_LIST`
- `ASSIGNMENT_LIST`

原因是公告、资源、作业都必须支持按 `classroomId` 查询。

## LMS 资源表

统一表名和字段：

- 表名：`course_resource`
- 文件类型字段：`file_type`

不使用 `resource` / `content_type` 作为最终公共表名字段。为了兼容 Java 代码，`ResourceDTO` 保留了 `getContentType()` / `setContentType()`，但内部仍映射到 `fileType`。

资源文件存储目录统一为：

`storage/resources/`

上传命令 `RESOURCE_UPLOAD` 第一版使用 `byte[]`，大小限制为 `SystemConstant.MAX_RESOURCE_UPLOAD_BYTES`，即 5MB。

## 当前用户传递方式

新模块统一采用显式参数：

```text
Handler -> Service(..., UserDTO currentUser) -> DAO
```

也就是说：

- 客户端只传 token，不传当前用户 ID。
- `RequestDispatcher` 根据 token 得到 `UserDTO currentUser`。
- `Handler` 把 `currentUser` 作为参数传给 Service。
- Service 在业务规则里使用 `currentUser.getRole()` / `currentUser.getUserId()` 做权限和归属校验。

`CurrentUserContext` 仍保留在服务端框架中，只作为兼容旧代码的过渡能力；新写模块不要依赖 ThreadLocal，也不要在自己的 handler 里 set/clear。

## Service 与 Handler 分工

`Handler` 负责：

- 接收原始 `Message`
- 获取 `requestId`
- 获取 `currentUser`
- 调用 Service
- 包装 `Message.success(requestId, data)`

`Service` 负责：

- 业务校验
- 权限细节
- 调用 DAO
- 事务边界

新的服务端接口尽量返回业务对象，不直接返回 `Message`。

选课、课堂、BBS、银行、商店、学籍、图书、宿舍模块此前存在 Handler 内直接写 SQL 的临时实现。当前本地工程已按最终标准拆为：

```text
CourseModuleHandler -> CourseServerServiceImpl -> CourseDAOImpl
ClassroomModuleHandler -> ClassroomServerServiceImpl -> ClassroomDAOImpl
BbsModuleHandler -> BbsServerServiceImpl -> BbsDAOImpl
BankModuleHandler -> BankServerServiceImpl -> BankDAOImpl
ShopModuleHandler -> ShopServerServiceImpl -> ShopDAOImpl
StudentModuleHandler -> StudentServerServiceImpl -> StudentDAOImpl
BookModuleHandler -> BookServerServiceImpl -> BookDAOImpl
DormModuleHandler -> DormServerServiceImpl -> DormDAOImpl
```

所以后续模块按“三层分离”写，Handler 全包不是最终形态。当前主要业务模块的 Handler 已经统一成命令注册与请求/响应适配层，SQL 统一下沉到 DAOImpl。

## 商店支付与银行扣款

统一采用“商店做外层事务，银行提供扣款能力”的方案。

用户点击支付订单时：

1. 客户端调用 `ORDER_PAY`
2. `ShopServerService.payOrder(...)` 开启事务
3. 商店校验订单状态、订单归属、库存
4. 商店在同一个事务中扣库存
5. 商店调用 `BankServerService.payWithinTransaction(connection, paymentRequest, currentUser)`
6. 银行在同一个 `Connection` 中扣款并写 `bank_transaction`
7. 商店更新订单为已支付
8. 全部成功才 commit，任意失败 rollback

`BANK_PAY` 保留为银行模块自己的对外支付命令，但商店支付订单时不建议客户端先调用 `BANK_PAY` 再调用 `ORDER_PAY`，这样会出现扣款成功但订单失败的不一致风险。

商店支付命令统一使用：

`ORDER_PAY`

旧的 `SHOP_PAY_ORDER` 已废弃，新代码统一调用 `ORDER_PAY`。

## 校园 BBS 命名对齐

BBS 公共命令已经登记，统一使用仓库现有的复数命名，避免再新增一套单数重复命令：

```text
BBS_LIST_BOARDS
BBS_SAVE_BOARD
BBS_DELETE_BOARD
BBS_LIST_POSTS
BBS_GET_POST
BBS_SAVE_POST
BBS_DELETE_POST
BBS_LIST_COMMENTS
BBS_SAVE_COMMENT
BBS_DELETE_COMMENT
BBS_AUDIT_POST
```

组员文档里的 `BBS_LIST_BOARD`、`BBS_LIST_POST`、`BBS_LIST_COMMENT` 视为同义描述，实际代码里统一改用上面的复数命令，不新增兼容别名。

BBS DTO 字段也以当前 common 包为准：

- `BbsBoardDTO(boardId, name, description, status)`
- `BbsPostDTO(postId, boardId, authorUserId, title, content, createdAt, status)`
- `BbsCommentDTO(commentId, postId, authorUserId, content, createdAt, status)`

数据库字段作者统一用 `author_user_id`，不再另写 `user_id`。如果后续需要帖子详情对象，再新增 `BbsPostDetailDTO`，不要把详情字段混进 `BbsPostDTO`。
